What is Cherm?

An offline code quality, concurrency, and architecture auditor built to catch production-breaking bugs before you commit.

100% Offline Zero Cloud Telemetry Web GUI (Port 3690) FastMCP 2.0 Bridge Terminal TUI Zero Config

Most developers rely on standard linters (ESLint, Flake8, Prettier). But linters only check syntax and formatting — they don't know if your database query will crash your server under a traffic burst, or if your checkout button can be rage-clicked 50 times to steal money.

On the other hand, cloud security tools (SonarQube, Snyk, Veracode) are slow, expensive, require uploading your source code to third-party servers, and only run after you push to CI/CD.

Cherm bridges this gap. It is a lightweight, zero-configuration auditor that inspects your code's architecture, race conditions, event loop bottlenecks, and credential leaks locally in milliseconds right on your laptop.

Concurrency & Multi-Tap

Simulates 50 rapid simultaneous clicks on checkout, payments, or votes. Flags missing debounce, idempotency keys, and database locks before double-spending occurs.

System Design Flaws

Catches architectural bottlenecks: unbounded queries pulling 500k rows into RAM (OOM), raw unpooled database connections, and wildcard CORS openings.

100% Private & Local

Zero code leaves your machine. No cloud API calls, no third-party accounts, and zero token costs. All AST and entropy analysis runs on local CPU.

How Cherm Works

A peek under the hood: how Cherm parses, stress-tests, and grades code in milliseconds without running untrusted code.

1

Step 1: Intelligent Ingestion & Context Filtering

You drop a file, point to a folder, or let an AI agent trigger an audit. Cherm immediately prunes build cache directories (.wrangler, .vercel, .next, node_modules, dist) and skips non-code assets (markdown, images, JSON configs) so you get zero false positives.

2

Step 2: 4-Layer Inspection Engine

Every genuine code file passes through four specialized deterministic analyzers:

  • Abstract Syntax Tree (AST) & Grammar Analyzer: Evaluates code hierarchy and structural complexity without executing dangerous code.
  • Concurrency & Multi-Tap Simulator: Identifies state-mutating operations (orders, payments, bookings, likes) and checks for button debouncing, idempotency keys, and database row locking.
  • System Design & Runtime Engine: Evaluates database pooling, query pagination, CORS headers, and Node.js event-loop blocking operations.
  • Shannon Entropy Secret Scanner: Uses mathematical entropy ($H = -\sum p \log_2 p$) to spot high-randomness tokens (API keys, private tokens) while intelligently ignoring import paths and URLs.
3

Step 3: Actionable Production Diagnostics

Cherm doesn't just output cryptic error codes like ERR_042. Every finding provides:

  • Plain English Explanation: Why this pattern is dangerous in real life.
  • Production Risk Scenario: What breaks when 200 users hit this simultaneously.
  • Exact Fix Recipe: Drop-in code snippet showing the defensive architecture.
The Shadow Copy Guarantee: When running in terminal mode, Cherm creates an isolated SHA-256 shadow copy in a temporary sandbox. Your original source files are never locked, written to, or corrupted.

Concurrency & Multi-Tap Attacks

How Cherm detects double-spending, inventory depletion, and duplicate mutation vulnerabilities.

[CONCURRENCY] Multi-Tap Vulnerability Simulated: 50 taps in 1.0s
The Problem

A user or automated bot clicks a "Transfer Funds", "Claim Reward", or "Submit Order" button multiple times simultaneously. Because requests arrive in parallel, all threads read the starting balance before any thread writes the deduction.

Real-World Loss Scenario

Double-spending: A customer with $100 balance drains $500 by submitting 5 parallel checkout requests. Or duplicate promo coupons are redeemed 50 times before state locks.

The 3-Layer Defense Cherm Verifies
  • Frontend: Immediate click debouncing or disabling button state (isSubmitting = true).
  • API Gateway: Mandatory Idempotency-Key header to deduplicate concurrent requests.
  • Database: Atomic SQL updates (UPDATE balance = balance - 100 WHERE balance >= 100) or distributed locking (Redis Redlock).

System Design & Scaling Flaws

Catches architectural bottlenecks that work in development but crash in production under load.

[DOS] Memory Explosion Unbounded Database Query
Vulnerable Pattern
# Fetches all rows without explicit pagination limit
users = db.session.query(User).all()
# or: SELECT * FROM transactions;
Production Risk

Works fine with 50 mock users in local development. When the table grows to 500,000 records, this query attempts to deserialize 600MB of rows into server RAM, triggering the Linux kernel Out-Of-Memory (OOM) killer to terminate your application process.

Architectural Fix
# Enforce strict cursor or page limits:
query.paginate(page=page, per_page=min(per_page, 100))
[STABILITY] DB Connection Starvation Raw Unpooled Connection
Vulnerable Pattern
# Opening fresh connection per request without a pool
conn = psycopg2.connect("postgresql://...")
Production Risk

A sudden burst of 200 concurrent HTTP requests initiates 200 separate TCP handshakes to PostgreSQL. PostgreSQL reaches its default max_connections = 100 limit and rejects all subsequent requests with connection refusal errors.

Architectural Fix
# Use a managed connection pool singleton:
engine = create_engine(url, pool_size=20, max_overflow=10)

Node.js & Next.js Antipatterns

Dedicated static analysis for modern JavaScript, TypeScript, and Next.js full-stack applications.

[NODEJS-PERF] Event Loop Starvation Synchronous I/O in Server Handler
Vulnerable Code
// Inside an Express route handler or Next.js Route Handler:
const data = fs.readFileSync(filePath, 'utf-8');
Production Impact

Node.js runs on a single-threaded event loop. Calling synchronous file I/O completely freezes the entire Node.js thread until disk read finishes. All incoming HTTP requests from other users stall, causing latency spikes from 15ms to 12,000ms and 504 Gateway Timeouts.

Architectural Fix
import { promises as fs } from 'fs';
const data = await fs.readFile(filePath, 'utf-8');
[NEXTJS-SECURITY] NEXT_PUBLIC Secret Leak Client Bundle Exposure
Vulnerable Code
// Exposing private secret key via NEXT_PUBLIC_
const secret = process.env.NEXT_PUBLIC_STRIPE_SECRET_KEY;
Production Impact

Next.js bakes any variable starting with NEXT_PUBLIC_ into the client-side JavaScript bundle downloaded by anyone visiting your site. An attacker opens Chrome DevTools Sources and extracts your private database connection string or Stripe secret key.

Architectural Fix

Remove the NEXT_PUBLIC_ prefix so the variable stays strictly on the server (Node/Edge runtime). Access via process.env.STRIPE_SECRET_KEY in Server Components or Server Actions.

Shadow Copy Architecture

How Cherm silently protects your original source code during every analysis operation.

The Problem: Why Analysis Tools Need Isolation

When you run any external analysis tool on a file, you are trusting that tool to be perfectly well-behaved. In practice, many analysis tools — especially security scanners, fuzzers, and instrumentation frameworks — can exhibit problematic behaviors:

  • File locking: Some tools open the target file with an exclusive lock, preventing your code editor from auto-saving while the tool runs.
  • Write-back side effects: Some tools write coverage data, instrumentation patches, or cache files next to the target or even inside the target file.
  • Crash corruption: If a scanner tool crashes mid-execution while it has the file open for writing, it can leave the file in an inconsistent state.
  • Parallel access conflicts: If you are running multiple Cherm analysis operations simultaneously (which the UI doesn't prevent you from doing across different terminal sessions), two tools accessing the same file simultaneously can produce corrupted results.

The Shadow Copy System eliminates all of these concerns by ensuring that every analysis tool operates exclusively on a temporary copy of your file, completely isolated from the original.

Step-by-Step: How a Shadow Copy is Created

The moment you trigger any analysis action in Cherm, the following sequence happens invisibly in the background before the tool is initialized:

  1. Path Resolution: Cherm calls os.path.abspath(filepath) to resolve the file's canonical absolute path. This handles cases where the path might be specified as a relative path or contain symbolic links.
  2. Path Hashing: The canonical path string is encoded to bytes and passed through SHA-256 using hashlib.sha256(path.encode()).hexdigest()[:8]. The first 8 hex characters are taken. This gives a stable, short unique identifier for the file's location.
  3. Shadow Name Construction: The shadow filename is built as {original_stem}_{8char_hash}{original_extension}. For example, main.py at path C:\ProjectA\ might become main_a3f9c021.py.
  4. Shadow Directory Preparation: os.makedirs(shadow_dir, exist_ok=True) ensures the cherm_shadow directory in %TEMP% exists.
  5. File Copy: shutil.copy2(original_path, shadow_path) copies the file including metadata. If this step fails for any reason (permissions error, disk full), Cherm falls back silently to using the original path and prints no error to the user — the tool will still run, just without isolation.
  6. Registry Update: The original → shadow path mapping is stored in a session-level dictionary _SHADOW_REGISTRY.
  7. Tool Invocation: The analysis tool receives the shadow path, not the original. From the tool's perspective, it is reading a regular file — it has no knowledge that it is operating on a copy.

Why the 8-Character SHA-256 Hash?

The hash exists to solve a specific problem: naming collisions. If you are a developer working across multiple projects, you might have a dozen files all named main.py, utils.py, or config.py in different directories. Without the hash, the shadow for C:\ProjectA\main.py and C:\ProjectB\main.py would both be named main.py in the temp folder and would overwrite each other.

The SHA-256 hash of the full absolute path ensures that the shadow name is unique for each unique path, even if the filename itself is identical. The hash is also deterministic — running the same file path through SHA-256 always produces the same hash — so the shadow file for a given original always ends up in the same temp location, making the registry lookups efficient.

The Self-Refreshing Nature of Shadows

This is a critical design decision: the shadow copy is recreated from scratch at the beginning of each action — not once per Cherm session. This means Cherm's shadow is always perfectly synchronized with the current state of your original file at the moment you triggered the action.

The practical consequence is powerful: you can have Cherm open all day, running scan after scan. Each time you run a scan, it picks up the absolute latest version of your file. There is no need to "refresh" Cherm or restart it when you make edits. Edit in your IDE → switch to Cherm → hit ENTER → Cherm scans the version with your latest changes. This is the core of Cherm's rapid-iteration workflow.

Automatic Cleanup via atexit

When Cherm starts up, it registers a cleanup function using Python's atexit.register(_cleanup_shadows). The atexit module guarantees that registered functions are called when the Python interpreter exits normally — whether via the ESC key, closing the terminal, or any unhandled exception that terminates the process. The cleanup function deletes the entire cherm_shadow folder and all its contents using shutil.rmtree().

This guarantees that Cherm leaves zero footprint on your machine after a session. The temp copies of your source code do not accumulate over time. If Cherm is killed forcefully (like SIGKILL on Linux or "End Task" on Windows), atexit does not fire, and the shadow folder may persist until your next Cherm session which will clean it up at startup, or until your OS's normal temp directory cleanup cycle.

Speed & Complexity Test

A two-phase analysis estimating algorithmic Big-O complexity through AST analysis, combined with a real runtime execution benchmark.

What you must understand before using this

  • Big-O notation: what O(1), O(log N), O(N), O(N log N), O(N²), O(2ⁿ) mean and how they affect scaling with large inputs.
  • What "nested loops" are and why they typically imply quadratic time complexity.
  • The difference between Time Complexity (number of operations) and Space Complexity (amount of memory used) — both matter for production systems.
  • Why algorithmic complexity matters: an O(N²) algorithm processing 1,000 items takes 1,000,000 operations. Processing 100,000 items takes 10,000,000,000 operations — a 10 billion operation jump for a 100x input size increase.
  • What a subprocess is: a separate OS process spawned by the parent program to run independently.

Why algorithmic complexity analysis matters in practice

The classic software development trap is writing code that works perfectly in development and falls apart in production. The root cause, in an enormous number of cases, is writing an algorithm that works fine for small datasets but scales catastrophically to production load. Developers routinely make the following mistakes without realizing it:

  • Using a nested loop to check for duplicates in a list instead of a hash set lookup — O(N²) instead of O(N).
  • Sorting inside a loop that runs N times — making the total complexity O(N² log N) instead of sorting once outside the loop for O(N log N).
  • Calling a database query inside a loop — producing N database round-trips instead of one batch query.
  • Using linear search (if x in list) repeatedly instead of converting to a set first for O(1) lookups.

The Speed and Complexity Test helps catch these patterns early — at the code writing stage — when they are cheap to fix, rather than after they have caused a production outage.

Phase 1: Static Big-O Estimation via AST Traversal

Cherm calculates theoretical algorithmic complexity by transforming your code into an Abstract Syntax Tree (AST) using Python's ast module. Rather than executing the code, it uses structural analysis based on established computer science theory to map code patterns to Big-O classes.

The Theoretical Basis (How to Verify the Output Yourself)

To verify Cherm's output manually, you must apply the same theoretical counting rules that Cherm uses under the hood. You can read your own code and look for these exact structures:

  1. Base Time: Every function starts at O(1) (Constant Time). Linear blocks of statements without loops or recursion are always O(1) because they take the same amount of time regardless of input size.
  2. Linear Time O(N): When Cherm detects an ast.For, ast.While, or a list comprehension (ast.ListComp), it assumes the loop iterates N times, where N is proportional to the input size. The complexity becomes O(N).
  3. Quadratic Time O(N²): The core theory of nested loops states that an inner loop executes its full cycle for every single iteration of the outer loop. If an ast.For node is found inside the body of another ast.For node, Cherm multiplies the complexity: O(N) × O(N) = O(N²). You can verify this by counting your indentation levels for loops.
  4. Exponential Time O(2ⁿ): If Cherm finds a function that calls itself (an ast.Call whose name matches the ast.FunctionDef), it flags a recursive pattern. Without memoization, naive recursive functions (like a Fibonacci calculator) spawn two branches per call, leading to O(2ⁿ) time complexity.
  5. Space Complexity: Cherm tracks theoretical memory scaling. It looks for ast.Call nodes involving .append(), .extend(), or dictionary insertions happening inside loops. If a list grows dynamically inside an O(N) loop, the theoretical space complexity is marked as O(N).

This theoretical approach allows Cherm to instantly classify scaling behavior. However, because it is purely structural, you must be aware of its limitations. If you write for i in range(3):, the loop bound is constant. Theoretically, this is O(1) time. But because Cherm only sees the ast.For structure, it conservatively grades it as O(N). You must use your own developer judgement to confirm if the N is truly variable.

def find_duplicates_slow(arr):

    duplicates = []
    for i in range(len(arr)):
        for j in range(i + 1, len(arr)):
            if arr[i] == arr[j] and arr[i] not in duplicates:
                duplicates.append(arr[i])
    return duplicates

    duplicates = set()

            duplicates.add(item)
        seen.add(item)
    return list(duplicates)

The Messiness Score Explained

The Messiness Score is a composite quality metric calculated from the following factors:

  • +2 points per level of loop nesting beyond depth 1
  • +1 point per decision statement (if, elif, try)
  • +1 point per function defined (large files with many functions score higher)
  • +1 point per 50 lines of code (length penalty)

A score of 0–5 is clean. 6–10 is getting complex but acceptable for sophisticated logic. Over 10 is a signal that the file or function should be split into smaller, more focused units. Cognitive complexity matters because developers can only hold a limited amount of code context in their working memory while debugging — simpler code is faster to debug and safer to modify.

⚠️ Key Limitation: Only Worst-Case Structural Depth is Measured Cherm counts loop nesting depth by AST structure. It does not analyze what the loop bound evaluates to at runtime. A nested loop where the inner loop runs exactly 3 times regardless of input size will still be flagged as O(N²) because structurally it has 2 levels of nesting. You must apply your own reasoning to determine whether a flagged complexity is a real concern for your input sizes.

Optimization Strategies (What to do when you get a bad score)

Replacing O(N²) nested loops with O(N) hash lookups

The most common performance issue Cherm flags is a nested loop used for lookup. Whenever you find yourself writing code like for item in list1: if item in list2:, the in check on a list is O(N). Convert list2 to a set first, and the lookup becomes O(1), making the total algorithm O(N) instead of O(N²).

Moving sort operations outside loops

If you need a sorted version of a collection, sort it once before any loops rather than inside a loop. Sorting inside a loop that runs N times makes your total complexity O(N² log N).

Using generators for large data processing

If you are processing large files or datasets, using Python generators (functions with yield) instead of building lists in memory can dramatically reduce peak memory usage, keeping space complexity O(1) instead of O(N).

The Problem CrossCheckV200 Solves

Most developers test their code by running it with the inputs they can think of — the happy path. A function that calculates a discount is tested with typical price and discount values. CrossCheckV200 takes a probabilistic approach: rather than asking "what could go wrong?", it systematically feeds every function every type of edge-case data it can generate, and watches to see which functions crash. How CrossCheckV200 Works for Python Files (Detailed)

Step 1: Safe Module Import via Shadow

CrossCheckV200 uses the shadow copy of your file.   • time.sleep is replaced with a no-op lambda.
  • Any curses operations are wrapped in a mock screen object that silently absorbs all draw calls.

Step 2: Function Extraction via inspect

Using Python's inspect.getmembers(module, inspect.isfunction), Cherm gets a list of all callable functions defined in the module. Step 3: Type-Aware Test Case Generation

For each function, inspect.get_annotations(func) reads the type hints. The fuzzer generates test inputs tailored to each parameter's declared type:

  • int: Generates 0, 1, -1, 2, 100, -100, 999999, -999999
  • float: Generates 0.0, 1.0, -1.0, 0.001, 1e10, float('inf'), float('nan')

  • list: Generates [], [1], [None], [1, 2, 3], [[]], list(range(1000))
  • dict: Generates {}, {"key": "value"}, {"key": None}
  • No annotation: Generates a mixed pool of all the above types.

Each combination of test inputs is run independently. For a function with 2 parameters, Cherm generates approximately 100 test cases per parameter, producing ~10,000 combinations, then samples 202 of them for the actual test run (to keep the test suite fast).

Step 4: Timeout-Protected Execution

Each function call is wrapped in a background thread with a hard timeout. If a function hangs indefinitely (infinite loop inside the function, blocking I/O that wasn't mocked), the thread is abandoned after a few seconds and the test case is marked as "timed out" rather than "crashed." Deep Dive: Coverage-Guided vs Generative Fuzzing

CrossCheckV200 utilizes a technique known as Generative Type-Aware Fuzzing. By looking at the type hints (e.g., def process(items: list):), it generates an aggressive but strictly bounded set of test inputs that historically cause edge-case crashes (like empty lists, lists containing None, or massive lists). This is fast and deterministic, making it suitable for a rapid IDE plugin.

In contrast, enterprise security teams use Coverage-Guided Fuzzing (like Google's OSS-Fuzz or the AFL fuzzer). Coverage-guided fuzzers instrument the binary at compile time. They send a completely random mutation of bytes into the function and observe which specific lines of assembly code were executed. If a specific mutated input causes a new, previously unseen code branch to execute (like bypassing an if size < 100 check), the fuzzer saves that input and mutates it further. Over millions of iterations, a coverage-guided fuzzer "learns" the internal structure of your code and can automatically solve complex string comparisons or checksums to dig deep into your logic and find memory corruption bugs.

While CrossCheckV200 doesn't do coverage tracking, its type-aware generative approach catches the most common 90% of business logic crashes in dynamic languages like Python without the massive CPU overhead of a coverage-guided engine.

What you must understand before using this

  • What variable scope is: a variable defined inside a function is local to that function and does not exist outside it.

Why Dead Code Accumulates

Dead code is not written intentionally — it accumulates through the natural evolution of software. Understanding how it gets there helps you prevent it:

  • Incomplete refactors: You replace a helper function with a built-in library call but forget to delete the old helper function at the bottom of the file.
  • Overly cautious development: You add a condition to guard against an edge case that can never actually occur given your data model, but write code after the guard clause that is now logically unreachable.
  • Debugging leftovers: You add a print() statement after a return during debugging — which is unreachable — and commit it.
  • Changed requirements: A feature is removed but the supporting functions and variables are not cleaned up because "someone might need them later."
  • Copy-paste programming: Variables are copied from a template into a function where only some of them are actually used.

Deep Dive: Graph Theory in Dead Code Elimination

Dead code elimination (DCE) is a standard optimization performed by modern compilers (like GCC or LLVM) before generating machine code. They use mathematical Graph Theory to do this safely.

A compiler builds a Control Flow Graph (CFG). In a CFG, every basic block of code (a sequence of statements with no branches) is a node, and every possible jump (an if, a while loop, a function call) is a directed edge connecting two nodes. The compiler starts at the entry point of the program (like main()) and traces every possible path along the edges.

Any node in the graph that cannot be reached by traversing edges from the entry point is mathematically proven to be unreachable code. The compiler simply deletes these disconnected subgraphs from memory before generating the final binary, making the executable smaller and faster. Cherm attempts to do a lightweight, single-file version of this graph reachability analysis by treating module-level code as the entry point and looking for disconnected function nodes.

What Makes a Number "Magic"?

Not every number in code is a magic number. The term specifically refers to numeric literals that carry domain-specific meaning that is invisible from the number itself. Consider the difference:

  • if index == 0: — Not magic. Zero is universally understood as the first element.
  • if status == 4: — Magic. What is status 4? "Cancelled"? "Pending review"? "Archived"?
  • for _ in range(3): — Possibly magic. Is 3 "max retries"? "Processing stages"? "Columns in a grid"?
  • if amount > 500: — Magic. Is 500 a free shipping threshold? A fraud detection limit? A discount tier?

The guiding question is: could someone who has never seen this codebase before understand what this number means from context alone? If the answer is no, it is a magic number.

Deep Dive: AST Constant Detection vs Lexical Regex

Why doesn't Cherm just use a regex like [0-9]+ to find magic numbers? Because regex cannot distinguish between syntax and semantics. A regex would match list[0], exit(1), and range(10) — flooding you with false positives because these are well-understood conventions, not "magic" domain numbers.

Instead, Cherm uses the ast module to walk the Abstract Syntax Tree. It specifically looks for ast.Constant nodes (which represent literal values like 75 or 3.14). Crucially, because it knows the context of the node, it applies intelligent filters:

  • Assignment Context: If the constant is the right-hand side of an assignment to a variable named with ALL_CAPS (like MAX_RETRIES = 5), Cherm ignores it. It recognizes this is already a named constant.
  • Array Index Context: If the constant is inside an ast.Subscript node (like items[0]), Cherm ignores 0, 1, and -1 as standard indexing patterns.
  • Conditional Context: Constants appearing in ast.Compare nodes (like if x > 1000:) are highly scrutinized because business logic limits are usually defined here.

By operating on the syntax tree rather than raw text, Cherm reduces false positives by over 95% compared to naive text scanning.

Deep Dive: Tokenization and Lexical Analysis

How does Cherm accurately count "pure code lines" versus "comment lines" in a language like Python where strings can span multiple lines and act as docstrings? A simple regex cannot handle this reliably.

Cherm uses Python's built-in tokenize module to perform lexical analysis. Lexical analysis is the first phase of a compiler. It reads the raw stream of characters and groups them into meaningful "tokens" (like IDENTIFIER, STRING, NUMBER, NEWLINE, COMMENT).

When Cherm processes your file, it doesn't look at lines of text; it looks at a stream of tokens. If it sees a tokenize.COMMENT token, it increments the comment count. If it sees a tokenize.STRING token that occurs as the very first statement inside a module, class, or function, it correctly identifies it as a docstring and counts its line span towards the documentation metric. This guarantees that a # symbol inside a printed string (e.g., print("Order #123")) is never accidentally counted as a comment line, a common flaw in simpler regex-based statistic tools.

Full Security Pentest

  • What a Python package dependency is and what requirements.txt or pyproject.toml is used for.
  • What "deserialization" means: the process of converting stored data back into a Python object. This is exploitable when the data source is untrusted (the attacker controls the serialized data).

Why Run Three Tools Instead of One?

No single security scanning tool catches everything. Each of the three tools uses a fundamentally different analysis technique and catches different classes of vulnerabilities. Running all three simultaneously gives you overlapping coverage — a vulnerability missed by Bandit's pattern library might be caught by Semgrep's AST rules, and a safe-looking codebase might still have a vulnerable third-party library caught by Safety.

Tool 1: Bandit — Python-Specific AST Security Scanning

Bandit walks your code's AST and applies a library of security test plugins. Each plugin looks for a specific security anti-pattern that is uniquely problematic in Python:

  • B301 (pickle): The pickle module can execute arbitrary Python code when deserializing untrusted data. Any use of pickle.loads() on data from the network is a critical vulnerability.
  • B324 (weak hashing): Using hashlib.md5() or hashlib.sha1() for security-sensitive purposes (password storage, digital signatures) is dangerous because both algorithms are cryptographically broken and subject to collision attacks.
  • B106 (hardcoded password): Flags string literals assigned to variables with names like "password", "passwd", or "secret".
  • B608 (SQL injection): Detects string formatting used to construct SQL queries.
  • B102 (exec): Flags use of the exec() built-in, which executes arbitrary Python code strings — a major risk if the input is user-controlled.

Tool 2: Semgrep — Universal AST Pattern Matching

Semgrep is a static analysis engine that matches patterns directly against the Abstract Syntax Tree, not raw text. This makes it far more precise than regex. A Semgrep rule can specify patterns like "find any function call to execute() where the first argument is a string concatenation involving a variable" — catching SQL injection even when expressed with f-strings, % formatting, or + concatenation, without any false positives from string literal concatenations that are safe.

Semgrep maintains an extensive community rule library covering not just security vulnerabilities but also correctness issues and performance anti-patterns across Python, JavaScript, Java, Go, Ruby, and many other languages.

Tool 3: Safety — Dependency Vulnerability Database

Safety checks your installed Python packages against PyUp.io's Safety DB, a continuously updated database of publicly disclosed vulnerabilities in open-source Python packages. Even perfectly written application code is insecure if it depends on a library with a known, unpatched vulnerability that an attacker can trigger through your application's normal public interface.

Safety runs against either your currently installed environment (pip freeze) or a specific requirements.txt file. For each vulnerable package found, it shows the CVE identifier, a plain-English description of the vulnerability, the affected version range, and the minimum safe version to upgrade to.

The OWASP Top 10 — Context for This Tool

The OWASP Top 10 represents the categories of vulnerabilities responsible for the majority of real-world web application breaches. Cherm's built-in OWASP audit specifically targets the following categories (listed by risk priority):

A01 — Broken Access Control

When file path operations accept user-supplied filenames without sanitization, attackers can use path traversal sequences (../) to read or write files outside the intended directory. Cherm looks for open(, os.path.join(, pathlib.Path( calls where the path argument contains a function parameter or variable rather than a pure string literal.

A03 — Injection (SQL, Command, LDAP)

SQL Injection occurs when user data is concatenated directly into SQL query strings instead of being passed as bound parameters. Cherm detects string concatenation (+), f-string interpolation (f"..."), and % formatting used in the same expression as SQL keywords (SELECT, INSERT, UPDATE, DELETE, WHERE). A02 — Cryptographic Failures

Cherm flags the use of weak or deprecated cryptographic functions: MD5 and SHA1 for security purposes, DES/3DES encryption, and random number generation using random.random() for security tokens (which should use secrets.token_hex() instead).

Deep Dive: Modern Web Application Defense Strategies

Fixing individual lines of code is treating the symptom. To truly secure a modern application, you must adopt an overarching architectural defense strategy. The industry standard approach involves Defense in Depth, meaning you do not rely on a single mitigation (like this regex audit) but rather layer multiple independent security controls.

Layer 1: The Code Level (What Cherm Does)

The first line of defense is secure coding practices. This means never trusting user input. Ever. You enforce this by:

  • Parameterized Queries: Using ORMs (like SQLAlchemy or Django ORM) or strict bound parameters in raw SQL (e.g., ? in SQLite, %s in psycopg2) to ensure user input is treated as literal data, never executable code.
  • Input Validation: Rejecting data that does not conform to strict type, length, and format requirements before it ever reaches your business logic.
  • Context-Aware Encoding: When echoing user data back to the browser, it must be HTML-encoded to prevent Cross-Site Scripting (XSS). If echoing into a JavaScript block, it must be JS-encoded. Frameworks like React or Vue handle HTML encoding by default, but legacy templating engines often require manual effort.

Layer 2: The Network Level (WAF and Egress Filtering)

Even if a developer makes a mistake and introduces a SQL injection, a Web Application Firewall (WAF) can often block the attack. WAFs inspect incoming HTTP traffic for malicious payloads (like the classic ' OR '1'='1' string) and drop the request before it hits your Python server. Similarly, Egress Filtering ensures that if an attacker achieves Remote Code Execution (RCE) via Command Injection, they cannot easily download further malware from the internet because outbound connections from the server are blocked.

Layer 3: The Environment Level (Least Privilege)

If an attacker successfully executes SQL injection, what can they do? If your application connects to the database as the root or postgres superuser, the attacker can drop tables, read password hashes, or even execute OS commands on the database server. By applying the Principle of Least Privilege, your app should connect using a restricted user account that only has SELECT, INSERT, UPDATE, DELETE privileges on specific tables, significantly limiting the blast radius of an injection flaw.

Enterprise Secrets Management Architecture

As applications scale beyond simple scripts, managing secrets via .env files becomes a liability. How do you distribute the .env file to 50 developers securely? How do you rotate a database password across 10 microservices simultaneously without downtime? Enterprise teams move beyond local environment variables to centralized secrets management architectures.

The HashiCorp Vault / AWS Secrets Manager Model

In a mature architecture, the application code itself contains no secrets. Not even in environment variables loaded at boot. Instead, the application only possesses an identity (like an AWS IAM Role attached to its EC2 instance or Kubernetes Pod). The workflow looks like this:

  1. The application boots up.
  2. Using its IAM Role, it authenticates to a central secrets vault (like AWS Secrets Manager, Azure Key Vault, or HashiCorp Vault).
  3. It requests the database credentials.
  4. The vault dynamically generates a temporary database password valid for only 1 hour, hands it to the application, and registers the password with the database.
  5. The application connects and does its work. If the password is leaked, it becomes useless in 60 minutes anyway.

Why This Matters to You

Even if you are writing a small Python script today, building the habit of abstracting configuration away from logic is critical. By using os.environ.get(), you decouple the secret from the code. Later, if you deploy this script to AWS Lambda or Google Cloud Functions, you simply inject those environment variables through the cloud console, and your code requires zero changes. This is the core philosophy behind the Twelve-Factor App methodology for building SaaS applications.

The Use Case: Rapid Iteration Without Context Switching

Every context switch between your code editor and your terminal has a cost — even if it is small, it breaks your concentration and adds friction to the edit-run-debug loop. When you are rapidly iterating on a script — make a fix, run it, see the output, make another fix — keeping that loop as tight as possible directly affects developer productivity and focus.

Cherm's Execute feature collapses the context switch into a single keypress. You are already in Cherm reviewing the file. You press ENTER on "Execute". Your script runs. You see the output. You press ENTER again to return to Cherm. The entire loop without opening a second terminal.

This is especially valuable for:

  • Scripts that accept interactive user input (input() calls).
  • CLI tools being tested with manual inputs.
  • Data processing scripts where you want to immediately verify the output after a logic change.
  • Developers working in SSH sessions where splitting the terminal into panes isn't always practical.

The Technical Process: What Happens During Execution

  1. curses teardown: Cherm calls curses.endwin() to gracefully exit curses mode. This restores the terminal to its normal, line-buffered "cooked mode" where regular text input and output work as expected.
  2. Header display: Cherm prints a visual separator and the filename being executed, so you have a clear visual cue that execution has begun and which file is running.
  3. Execution prefix selection: Cherm determines the correct command based on file extension: .py → python (or python3), .js → node, .sh → bash, compiled binaries → direct path execution.
  4. Process spawn: subprocess.run(command, shell=True) is called with inherited stdin, stdout, and stderr from the parent Cherm process. Your script runs with full access to the terminal — your script's input() waits for you to type, and print() writes directly to your screen.
  5. Wait for completion: Cherm blocks until your script exits. The exit code is captured.
  6. Result display: The exit code is displayed. Exit code 0 = OK (green). Any other exit code = Error (red).
  7. Pause for user: Cherm prints "Press ENTER to return to Cherm..." and waits for you to review the output before the curses UI is re-drawn.

Deep Dive: Process Lifecycle and OS-Level Isolation

When you trigger the Execute function, Cherm is acting as a parent process spawning a child process. Understanding this process tree is fundamental to systems programming.

Memory Isolation

Because Cherm uses subprocess.run(), the executed script runs in an entirely separate memory space. If your script has a catastrophic memory leak that consumes 16GB of RAM and is killed by the OS Out-Of-Memory (OOM) killer, Cherm itself remains unaffected and responsive. If Cherm had attempted to run your script using Python's exec() within the same process, a crash in your script would crash the entire Cherm IDE.

File Descriptor Inheritance

Why does the print() statement in your script appear on your screen, even though it's running in a separate process? When an operating system forks a new process, the child inherits the parent's standard file descriptors: 0 (stdin), 1 (stdout), and 2 (stderr). Cherm deliberately does not capture or redirect these streams. As a result, the OS routes the child process's output directly to the terminal emulator you are viewing, bypassing Cherm's internal logic entirely. This is why interactive scripts with input() work flawlessly.

The Role of the Exit Code

The exit code (status code) is the only piece of information a child process is guaranteed to pass back to its parent. In POSIX systems (Linux, macOS, Unix), this is an 8-bit integer (0-255). Python abstracts this: if a script finishes normally, it calls sys.exit(0) implicitly. If an unhandled exception reaches the top of the stack, the Python interpreter prints the traceback to stderr and calls sys.exit(1). Cherm captures this integer to color-code the success/failure message at the end of the run.

Interpreting the Results

  • 200 OK: The endpoint is alive and responding normally. No action needed.
  • 401 Unauthorized: The endpoint exists and is reachable, but your request lacks authentication. This is actually a healthy response — it confirms the URL is valid. The 401 is expected if you're hitting an authenticated endpoint without credentials in the GET request.
  • 403 Forbidden: The endpoint exists and authentication was provided, but access is denied. Similar to 401 — not a URL problem, an auth problem.
  • 404 Not Found: The server was reached, but the specific resource path doesn't exist. This URL in your code is broken — update or remove it.
  • DNS Error: The domain name could not be resolved. Either the domain no longer exists, the service was shut down, or you are trying to reach an internal service URL that is only accessible inside a specific network (like a VPN or company intranet).

Deep Dive: Pager Memory Management and Terminal Rendering

The concept of a "pager" dates back to the early days of Unix when terminals were physical teletype machines printing on paper. The command cat (concatenate) would dump the whole file to the printer, wasting reams of paper. Pagers like more and later less were invented to pause the output after one screenful.

Cherm implements its own modern virtual pager using curses. When you view a file, Cherm maintains a "viewport" — a sliding window defined by a start_line index and the terminal's physical height (usually 24 to 50 rows). Every time you press the Down arrow, Cherm increments start_line by 1.

Critically, the curses library uses a double-buffering technique. When you scroll, Cherm clears an off-screen memory buffer, writes the 40 lines of text into that buffer, and then calls screen.refresh(). The curses engine then calculates the diff between the off-screen buffer and what is currently displayed on your physical screen, and sends only the minimal terminal escape sequences required to update the changed characters. This differential rendering is what allows terminal UIs to feel so blazing fast even over slow SSH connections.

Deep Dive: X11 Selection Buffers vs Wayland Clipboards

While copy-pasting feels like a universal operating system feature, its underlying architecture is highly fragmented, which is why Cherm has to dynamically branch its logic.

On Windows and macOS, the clipboard is a centralized OS service. Programs simply make a system call to read or write data to it.

On Linux running the older X11 display server, there is no centralized clipboard. Instead, X11 uses "Selection Buffers" (PRIMARY, SECONDARY, and CLIPBOARD). When you copy text, the application doesn't send the text to a central server; instead, it tells the X server "I own the CLIPBOARD selection." When another application wants to paste, it asks the X server "Who owns the CLIPBOARD?", contacts that application, and requests the data. If the application you copied from closes before you paste, the text is lost! This is why Cherm shells out to xclip, which artificially keeps itself alive just long enough to serve the selection to the next paste request.

Modern Linux uses Wayland, which fundamentally redesigned this for security. In Wayland, applications cannot snoop on each other's clipboards without the compositor's explicit permission. Wayland uses the wl-clipboard protocol to manage this exchange securely.

Deep Dive: The Object Database and Merkle Trees

When you use Cherm's "Git Add" and "Git Commit" features, it feels like you are saving files. In reality, you are interacting with a cryptographic Merkle Tree stored inside the hidden .git/objects/ directory.

Git does not store diffs; it stores snapshots. When you execute git add my_file.py, Git takes the entire content of that file, compresses it with zlib, calculates its SHA-1 hash (e.g., 7f3d9a...), and saves it as a "blob" object in the database. The Staging Area (or Index) is simply a binary file (.git/index) that maps the filename "my_file.py" to that specific SHA-1 hash.

When you execute git commit from Cherm, Git creates a "tree" object. This tree lists the names of all directories and files and their corresponding blob hashes. Finally, Git creates a "commit" object containing your commit message, the author details, a pointer to the tree object, and a pointer to the parent commit. Because every object's identity is derived from its cryptographic hash, the entire history is tamper-proof — changing a single byte in a file from a year ago would change its blob hash, which would change the tree hash, which would change the commit hash, cascading all the way to the present HEAD.

Deep Dive: The Myers Diff Algorithm

Have you ever wondered how Git (and Cherm, via Python's difflib) calculates exactly which lines changed? It isn't trivial. If you insert a single new line at the top of a 1,000-line file, a naive line-by-line comparison would say that all 1,000 lines are different because line 1 is now line 2, line 2 is now line 3, etc.

To solve this, diff tools use the Longest Common Subsequence (LCS) problem, typically solved using Eugene Myers' 1986 algorithm. The Myers algorithm visualizes the two files as an X/Y grid, where the X-axis is the old file and the Y-axis is the new file. It attempts to find the shortest path from the top-left (start of files) to the bottom-right (end of files).

Moving right means a line was deleted. Moving down means a line was added. Moving diagonally means the lines match. The algorithm aggressively hunts for diagonal paths (matching lines) to minimize the number of right/down moves (edits). Once it finds this optimal path, it translates the movements into the unified diff format you see on screen, successfully re-synchronizing itself even after large blocks of inserted or deleted code.
